# Deviations / audit trail (all before any model was executed)

No LLM has been run under this track. Entries below are design revisions made while building the infrastructure, recorded so the final spec is not mistaken for a first draft.

1. **View rule 3 changed (drop duplicates → merge identical lines).** First draft dropped exact-duplicate lines because the production upload validator rejects duplicate rows. Measurement showed that removed 42% of whole-quantity lines and about ₹13.8 lakh (32%) of their sales, which would make every total unrepresentative of the register. Replaced by merging lines sharing (date, product, unit price) with summed quantity: total sales and units of the retained lines are preserved exactly. Consequence: "one row" is no longer "one bill line", so the three entry-grain tasks (count of entries, average entry value, largest entry) were replaced by units-in-February, mean daily units, and highest daily total. Spec v1 was regenerated once, before execution; its hash is recorded in every run.
2. **Scorer bug fixed in unit testing:** a "Month Year" string such as "January 2025" left "25" behind as a number. Found by `tests/unit/test_llm_eval_scoring.py` before any run; no run used the old scorer for results (the earlier smoke run is not a result).
3. **Primary clock condition:** DecisionGPT's chat windows are relative to `date.today()`; the primary condition fixes the evaluation clock at 2025-03-31 (as if the owner asks right after the data period) and the real-clock condition is kept as secondary. Production code is untouched.
4. **GST tasks are a supplementary track:** the production schema cannot store GST, so DecisionGPT cannot receive it; the baseline gets `gst_pct` only on those four tasks. They are reported separately and never mixed into the primary track.
5. **2026-10-08 architecture audit (before any model was executed): the evaluation target was corrected.** `audit/architecture.py` + `ARCHITECTURE_AUDIT_2026-10-08.md` show the production business-analytics chat path is a fixed-intent router with template answers; an LLM (when configured) only rephrases four non-analytics intents, and none of the 27 frozen questions can reach an LLM call. The system is therefore named **"DecisionGPT production chat path (fixed-intent router + template answers) - Target A"** in runs and reports; the LLM + pandas system is named **"Reference tool-use system"** (not a simpler baseline, not DecisionGPT). `run_evaluation` now reports two distinct blockers (`production_path_not_llm_powered`, `provider_not_configured`) and refuses to run while either holds. `tasks/execution_subsets_v1.json` is a derived classification of the frozen task ids (A/B1/B2/C/D); the frozen spec `tasks_v1.json` was not edited. The clock-freeze mechanism now also covers `churn_service`; the documented smallest production change (`clock.today()`) was not implemented.
6. **2026-10-08 (later): an LLM analytics path was added to the production chat; the evaluation target changed from Target A to Target B.** `ARCHITECTURE_UPDATE_LLM_ANALYTICS_PATH_2026-10-08.md` records it. The business chat now interprets a question with an LLM into a strict structured request, runs a deterministic query engine, and writes the answer from the verified result (`path=llm_analytics`); the legacy router remains the flagged fallback (`path=legacy_router`). Consequences recorded here, all before any model was executed: (a) the `decisiongpt` system label in `SYSTEM_LABELS` now names the LLM analytics path (Target B) and states that legacy-served answers are not LLM answers; (b) preflight blockers are now computed from the live code audit (`production_path_not_llm_powered` only if the path is missing or `ANALYTICS_LLM_ENABLED=false`; `provider_not_configured` otherwise), so the single remaining blocker is the provider; (c) the evaluation clock is now the production clock abstraction `app.core.clock.reference_date` (no more patching of `datetime.date` in four modules); (d) run rows record `path`, and run metadata records `decisiongpt_answer_paths` / `decisiongpt_attempts_not_served_by_llm_analytics_path`; (e) the 24/27 router-failure analysis and the A/B1/B2/C classification in `ARCHITECTURE_AUDIT_2026-10-08.md` describe the LEGACY router and remain correct for it. The frozen spec, tolerances, ground truth and scorer were not changed; a mocked-LLM architecture dry-run is in `audit/llm_path_dryrun.json` and is not a research result.
7. **2026-10-08 (final pre-experiment readiness gate; all changes made BEFORE any model was executed, none to the frozen spec, tolerances, ground truth or scorer).** See `READINESS_GATE_2026-10-08.md` / `audit/readiness_gate.json`. (a) **Fail-closed preflight**: the runner now refuses to start if the task-spec hash differs from `98f37037…` ("FROZEN TASK SPECIFICATION CHANGED — EVALUATION BLOCKED."), the manifest differs from `94aa419c…` ("EXPERIMENT MANIFEST CHANGED — EVALUATION BLOCKED."), the evaluation clock is not deterministic/scoped, the adapter is unavailable, or the retry layer differs from `backend/requirements.txt`; it also blocks when `LLM_MODEL` is empty (the code-default model is not accepted: the exact model must be named) or the provider is not one of openai/openai_compatible/anthropic. (b) **Environment drift fixed**: `tenacity==9.0.0` is declared but was not installed in the venv, so the client's optional-import fallback silently disabled ALL provider retries; it is now installed and the runner fails closed if that recurs. (c) **Default conditions are `asof` only**: the secondary `realclock` condition depends on today's date and is not reproducible; it remains an explicit opt-in. (d) **Measurement**: per-call role (interpreter / explainer / baseline), HTTP attempt count (counted inside `LLMClient._post`, retries never hidden, also for finally-failed calls), latency including retries, provider-reported tokens, echoed model id; engine and stage timings from the production audit record; token totals sum the calls that returned usage with the counts of those that did not (nothing estimated); cost only from a verified price for the exact returned model, failed calls excluded (lower bound flagged); p95 reported only with >= 20 observations. (e) **Attempt accounting** (`attempt_accounting.py`): every DecisionGPT attempt is classified llm_path / unsupported / legacy_fallback / infrastructure_failure with a failure category; a legacy-router answer is never an LLM-path success (its would-be verdict is kept as `score_unadjusted`); GST-track refusals are `unsupported_by_design` and excluded from agreement rates (neither failure nor success). (f) **Ground-truth isolation guard**: every interpreter request is whitelist-checked (fixed instructions + minimal context + a frozen question verbatim) and scanned for ground-truth numeric fragments; a violating request is not sent and aborts the run. (g) **Report language**: metrics are called "agreement with ground truth" / "LLM-path" results, never "DecisionGPT accuracy"; every report states that the deterministic engine is the numerical authority and that the evaluated component is the natural-language-to-structured-request layer; an exact-match structured-request accuracy is NOT available (no gold requests exist in the frozen spec). (h) **`mock` command**: wire-level fake-provider infrastructure validation (flagged mock, `research_result=false`, banner on every page, never shown as a result). (i) the interpreter/explainer audit record gained `attempts`, `response_model` and `error`; `LLMClient` records `last_attempts` and `last_response_model` (measurement only).

8. **2026-10-13 (BEFORE any model was executed; frozen spec `98f37037…`, ground truth, scorer, tolerances and manifest `94aa419c…` untouched): the evaluated provider changed from an OpenAI-compatible chat model to TypeSafe AI Jev.** Jev returns typed decisions (choice / score / yes-no), not text, so: (a) the system under test is now "typed decisions about the question + deterministic extraction of periods/products/limits -> the same closed `Interpretation` schema -> the same deterministic query engine"; (b) there is no explainer call: answers are deterministic templates, so `explainer` metrics and the number/causal guards no longer exist; (c) one request per attempt, no retries (the retry layer is removed); (d) the ground-truth isolation guard, mock provider (`mock_llm.py`), instrumentation (`llm_instrument.py`), runner preflight/labels/metadata and report text were ported to the Jev wire format; the architecture audit JSON was regenerated; (e) the reference tool-use system (`llm_code_baseline`) needs code generation and CANNOT run on Jev - `run` refuses it explicitly and the readiness-gate document records it as not runnable; (f) the interpreter is no longer a prompt but a fixed set of typed questions, so its hash is recorded as `interpreter_questions_sha256`. The 27 frozen questions were dry-run through the full production chat route with a MOCKED Jev: 23/23 primary answers equal the independent ground-truth engine and 4/4 GST questions are refused (`audit/llm_path_dryrun.json`; NOT a research result). Nothing about Jev's real classification accuracy is known.

9. **2026-10-14 (first live run; frozen spec `98f37037…`, ground truth, scorer, tolerances, task wording and manifest `94aa419c…` untouched): partial pilot, 6 of 27 tasks x 1 repeat (frozen protocol: 5).** The runner gained `--task-ids`, `--repeats`, `--max-requests` and `--selection-file` so a subset can be run reproducibly; a subset or reduced-repeat run is recorded as `run_type=partial_pilot`, can never reach status COMPLETED, and stores the attempted / not-attempted ids and the pre-run selection record (`pilots/pilot_2026-10-14_selection.json`, written before any live answer was seen). Selection rule: the first task of each of the six categories in frozen spec order (A01, B01, C01, D01, F01 primary; E01 supplementary GST). Reason for the small size: the provider's credit unit is undefined in its documentation and the account balance cannot be inspected, so the request count was capped at 6 (`--max-requests 6`; measured at 6 provider calls, 0 errors). `pricing.json` was added from the published list price so cost is computed only from provider-reported token counts. Result: run `run_20261014T042125Z_0daf9d32`, 5/5 primary tasks correct, the GST task fell back to the standard assistant on low confidence. This is a pilot: it supports no accuracy estimate, no comparison, and nothing about the 21 unattempted tasks or repeats 2-5. B2 remains not runnable on Jev.

10. **2026-10-14 (stage 2; frozen spec, ground truth, scorer, tolerances, task wording and manifest unchanged): second partial run, the 21 frozen tasks not attempted in the pilot x 1 repeat (frozen protocol: 5), cap 21.** Selection pre-registered in `pilots/stage2_PROPOSAL_not_executed.json` (file unchanged by the run; execution record in `pilots/stage2_EXECUTED_run_20261014T054253Z_a147cc55.json`). Run `run_20261014T054253Z_a147cc55`: 21 provider requests, 0 errors, 18 of 18 primary tasks correct, GST tasks E02 clarification / E03 low-confidence fallback / E04 declined as unsupported. Together with the pilot every frozen task has been attempted once; this is still NOT the five-repeat frozen protocol, the two runs remain separate records, and the sample (23 scored tasks, one store, 89 days, one repeat) does not support an accuracy estimate or any comparison.

11. **2026-10-14 (provider migration to OpenAI; frozen spec `98f37037…`, ground truth, scorer, tolerances, task wording and manifest `94aa419c…` untouched): the active provider changed from TypeSafe AI Jev to OpenAI.** The system under test is now: OpenAI classification into the same closed labels through a strict JSON schema -> the same deterministic extraction -> the same closed `Interpretation` schema -> the same deterministic query engine -> an optional model restatement of the verified facts that is shown only if it adds no number, causal claim or advice. Consequences recorded here: (a) up to TWO provider requests per attempt (classification + restatement) instead of one; (b) confidence is the model's SELF-REPORTED value, not a provider probability; (c) the retry policy is bounded (<= 1 retry for rate-limit / connection errors; timeouts never retried) instead of none; (d) no seed or sampling parameter is set; (e) cost is estimated from the published per-token price in `pricing.json`. The earlier Jev runs (pilot `run_20261014T042125Z_0daf9d32` and stage 2 `run_20261014T054253Z_a147cc55`) are unchanged and remain labelled `typesafe-jev`; OpenAI results are stored as separate runs and are never pooled with them into one accuracy figure. No OpenAI evaluation had been executed when this entry was written.

12. **2026-10-14 (OpenAI smoke evaluation; frozen spec, ground truth, scorer, tolerances and manifest unchanged):** first OpenAI run, 6 of 27 tasks x 1 repeat, request cap 12, run `run_20261014T172246Z_f320dc9f`, model `gpt-5-mini` (served `gpt-5-mini-2025-08-07`): 11 requests (6 classification + 5 validated explanation), 0 errors, 5/5 primary tasks correct, GST task E01 answered with a clarifying question. Two harness changes preceded it and are recorded here: (a) reasoning-model families (gpt-5 / o-series) are sent `reasoning.effort=low` and a larger output allowance so hidden reasoning cannot exhaust the cap (the isolation whitelist permits exactly that fixed setting); (b) the request cap is enforced per request in the recorder, not only per attempt. Not an accuracy estimate; not pooled with the Jev runs.

13. **2026-10-15 (implementation change AFTER the OpenAI smoke run; frozen spec, ground truth, scorer, tolerances and manifest unchanged; no run executed):** the optional explanation step now has a deterministic repetition / unsupported-claim guard and is requested only for lists of 3+ rows; the explainer system prompt was reworded (hash recorded per run in `explainer_system_sha256`); a deterministic capability policy answers questions about data the records do not hold (GST/tax, region, payment mode, marketing channel) with one fixed refusal, in both the AI path and the standard assistant; `ANALYTICS_EXPLAIN_ENABLED=false` was verified to send no explanation request. Smoke run `run_20261014T172246Z_f320dc9f` was produced WITHOUT any of these changes and its stored answers, scores and E01 clarification are unchanged and must not be read as results of the new code. A future evaluation with these changes must be a NEW run with its own run id; request counts per attempt will differ (1 for most tasks, 2 only for lists), and it is never pooled with earlier runs. See `docs/OPENAI_INTEGRATION.md`.

Any change after the first real run starts must be added here as a new entry (never a silent edit) and all runs re-scored.
